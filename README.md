# Allergy Risk Monitoring API

Backend системы мониторинга риска аллергических реакций: Django 6.1,
django-modern-rest, msgspec и MongoDB. Эмулятор получает данные Open-Meteo,
нормализует их и передаёт этому API. Backend не вызывает внешний погодный сервис.
Клиент и эмулятор разворачиваются отдельно.

## Запуск

Команды выполняются из `lab_2/project`. Нужен запущенный MongoDB Server 7.0+.

```bash
uv sync --locked
```

Если `.env` ещё нет, создайте его и заполните значения:

```bash
cp .env.example .env
```

Для ключа эмулятора сгенерируйте случайное значение и сохраните его
в `INGEST_API_KEY` в `.env` и в настройках эмулятора:

```bash
uv run python -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Ключ должен содержать от 32 до 256 символов. Если ключ не задан,
приём измерений отключён и возвращает 503. Не передавайте этот ключ веб-клиенту.

```bash
uv run python manage.py migrate
uv run python manage.py createoperator operator
uv run python manage.py runserver
```

`createoperator` интерактивно запрашивает пароль дважды, проверяет его
валидаторами Django и создаёт активного сотрудника без прав суперпользователя.
Пароль не передаётся в аргументах командной строки и хранится в виде хеша.
Команду можно выполнять на сервере для каждого сотрудника. Смена пароля:

```bash
uv run python manage.py changepassword operator
```

Публичной регистрации нет. Для создания суперпользователя доступна
стандартная серверная команда Django `createsuperuser`.

## Формат измерения

Эмулятор отправляет одно измерение за запрос:

```http
POST /api/v1/measurements/
Content-Type: application/json
X-Ingest-Key: <ключ эмулятора>
```

```json
{
  "station_id": "minsk-center",
  "observed_at": "2026-11-04T10:00:00Z",
  "latitude": 53.9,
  "longitude": 27.5667,
  "location_name": "Минск",
  "source": "open-meteo",
  "metrics": {
    "birch_pollen": 15.0,
    "grass_pollen": 30.0,
    "ragweed_pollen": null,
    "pm2_5": 12.3,
    "european_aqi": 28.0,
    "temperature_2m": 8.5,
    "relative_humidity_2m": 73.0
  }
}
```

Ответ 201 содержит эти поля и дополнительные `id`, `location_id`, `risk_score`, `risk_level`,
`created_at`, `updated_at`. `id` — строка MongoDB ObjectId.
`location_name` необязателен, `source` по умолчанию `open-meteo`.

Допустимые показатели и единицы внутреннего контракта:

| Показатели | Единицы |
| --- | --- |
| `alder_pollen`, `birch_pollen`, `grass_pollen`, `mugwort_pollen`, `olive_pollen`, `ragweed_pollen` | grains/m³ |
| `pm10`, `pm2_5`, `carbon_monoxide`, `nitrogen_dioxide`, `sulphur_dioxide`, `ozone` | µg/m³ |
| `european_aqi`, `us_aqi` | Индексы соответствующего стандарта |
| `temperature_2m` | °C |
| `relative_humidity_2m` | % |

В словаре `metrics` должен присутствовать хотя бы один известный показатель
с числовым значением. `null` означает отсутствие данных, а не ноль.
Неизвестные поля и показатели отклоняются. Все числа должны быть конечными;
концентрации и индексы неотрицательные, влажность — 0–100, координаты — в
географических пределах. Отрицательная температура допустима.
Размер тела запроса ограничен 64 КиБ.

`observed_at` — время исходного наблюдения, а не время отправки. Обязателен
часовой пояс (`Z` или UTC offset). В базе время нормализуется в UTC с точностью
до миллисекунд. Можно передавать исторические и прогнозные значения.
Комбинация `station_id + latitude + longitude + observed_at` уникальна: повтор возвращает 409 и не создаёт
дубликат. При повторной отправке после сетевой ошибки эмулятор может сверить
существующую запись; исправлять её ключом эмулятора нельзя.

`risk_score` и `risk_level` рассчитывает только backend, в `api/risk.py`.
Они не принимаются в POST/PUT: старый payload с `risk_score` будет отклонён.
Эмулятор передаёт исходные значения показателей, без формулы риска.

Серверная учебная формула:
`risk_score = round(min(100, max(100 × pollen / 100 grains/m³, european_aqi)), 2)`.
В максимум входят все известные виды пыльцы и европейский AQI; отсутствующие
значения исключаются. Если все они отсутствуют, сохраняются `risk_score: null`
и `risk_level: null`, а остальные исходные показатели не теряются.
Категории: `low` — [0,25), `moderate` — [25,50), `high` — [50,75),
`very_high` — [75,100]. Это внутренний учебный индекс, не медицинская модель.
При PUT backend пересчитывает риск из обновлённых исходных показателей.

`PUT` принимает ту же полную структуру, что и `POST`. Идентификатор и время
создания сохраняются; время изменения обновляется. `DELETE` возвращает 204
без тела. PATCH и массовое удаление не предусмотрены.

## История и фильтры

Пример запроса для построения графика:

```text
/api/v1/measurements/?station_id=minsk-center&time_from=2026-11-01T00:00:00Z&time_to=2026-11-04T23:59:59Z&order=asc&limit=500
```

| Параметры | Значение |
| --- | --- |
| `location_id` | Идентификатор из `/api/v1/locations/` |
| `station_id`, `source` | Точное совпадение |
| `time_from`, `time_to` | Включительные границы времени наблюдения с часовым поясом |
| `risk_min`, `risk_max` | Включительные границы 0–100 |
| `risk_level` | `low`, `moderate`, `high`, `very_high` |
| `latitude_min`, `latitude_max`, `longitude_min`, `longitude_max` | Географический прямоугольник, включительные границы |
| `order` | `asc` или `desc`, по умолчанию `desc` |
| `limit` | 1–500, по умолчанию 100 |
| `offset` | 0–100000, по умолчанию 0 |

Все фильтры сочетаются через AND. Обратные диапазоны возвращают 400.
Дата без времени и часового пояса не принимается; `+` в offset часового пояса
в URL нужно кодировать как `%2B`. Для UTC проще использовать `Z`.

Ответ списка:

```json
{"items": [], "limit": 100, "offset": 0, "has_more": false}
```

При `has_more=true` запросите следующую страницу с `offset + limit`.
Сортировка стабильна по `observed_at`, затем по `id`. При одновременном
добавлении или удалении данных страницы с offset могут смещаться.
`/latest/` использует те же фильтры, но всегда выбирает максимальное
`observed_at`, независимо от `order`, `limit` и `offset`. Если данных нет,
список возвращает пустой массив `items`, а `/latest/` и запрос по id — 404.

## Сессионная аутентификация

Пользователи и сессии хранятся в обычных коллекциях MongoDB.
Фронтенд следует размещать на том же origin либо проксировать `/api/` к backend.
Для fetch передавайте `credentials: 'include'`.

1. Выполните `GET /api/v1/auth/csrf/`. Сервер установит cookie `csrftoken`
   и вернёт `csrf_token` в JSON.
2. Выполните `POST /api/v1/auth/login/` с JSON
   `{"username":"operator","password":"..."}`, cookie `csrftoken` и заголовком
   `X-CSRFToken` со значением из первого ответа.
3. Сервер установит HttpOnly cookie `sessionid`. Ответ содержит
   `id`, `username`, `is_staff`. После входа Django меняет CSRF-токен:
   повторите `GET /auth/csrf/` для получения актуального значения.
4. Для PUT, DELETE и logout отправляйте cookie сессии, CSRF cookie
   и актуальный `X-CSRFToken`. Права изменения есть только при `is_staff=true`.
5. `POST /api/v1/auth/logout/` удаляет текущую сессию и возвращает 204.
   Остальные сессии этого пользователя не завершаются.

Login ограничен 5 запросами в минуту на IP, приём измерений — 120.
При превышении лимита возвращается 429. По умолчанию Django cache локален
процессу; для нескольких воркеров настройте общий cache и ограничение запросов
на reverse proxy. `REMOTE_ADDR` должен отражать доверенный адрес клиента.

## Ошибки и журналирование

Ошибки API возвращаются в формате DMR `{"detail":[{"msg":"..."}]}`
с дополнительными стандартными полями ошибок при наличии:

- 400 — некорректный диапазон или значения измерения
- 401 — отсутствует или неверен ключ/сессия/пароль
- 403 — ошибка CSRF или недостаточно прав
- 404 — измерение не найдено
- 409 — конфликт станции, координат и времени
- 413 — превышен размер тела запроса
- 422 — ошибка схемы данных
- 429 — превышение лимита запросов
- 503 — временно недоступна база или не настроен приём данных

Недоступность Open-Meteo обрабатывает эмулятор: повторные попытки с задержкой,
без отправки вымышленных нулевых значений. В сохранённых данных `null` означает
отсутствующий показатель. Недоступность MongoDB обрабатывает backend, без
раскрытия строки подключения клиенту. При 503 эмулятор должен сохранить
неотправленные данные и повторить запрос позднее.

Основные операции и запросы записываются в stdout/stderr через logging.
В журнал не включаются пароли, cookie, ключи и тела запросов. API-ответы содержат
`X-Request-ID`, соответствующий записи в журнале.

## Конфигурация

`.env` автоматически читается из корня проекта; окружение процесса имеет
приоритет. Содержимое `.env` не попадает в Git.

| Переменная | Назначение |
| --- | --- |
| `MONGODB_URI` | URI MongoDB, по умолчанию `mongodb://localhost:27017` |
| `MONGODB_DATABASE` | Имя базы, по умолчанию `project` |
| `INGEST_API_KEY` | Отдельный случайный ключ эмулятора |
| `DJANGO_DEBUG` | По умолчанию `true`; на сервере задайте `false` |
| `DJANGO_SECRET_KEY` | Обязателен при DEBUG=false, задайте случайный постоянный секрет |
| `DJANGO_ALLOWED_HOSTS` | Допустимые хосты через запятую |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Доверенные origin со схемой через запятую, если нужны |

Вне отладки cookies передаются только по HTTPS. Валидация ответов включена.
При проксировании TLS настройте доверие к proxy в соответствии с инфраструктурой.

## Хранение и структура

`Measurement` — обычная коллекция с индексами по станции, времени и риску,
с уникальным индексом станции, координат и времени. Специальная time series коллекция
не используется, поскольку API поддерживает произвольную замену измерений.
Старые документы автоматически не удаляются. Миграция не переводит уже
существующую time series коллекцию в обычную.

- `api/schemas.py` — входной и выходной контракт
- `api/controllers.py`, `api/urls.py` — транспортный слой REST
- `api/services.py` — проверка данных и преобразование DTO
- `api/risk.py` — серверный расчёт риска и его категории
- `api/repository.py`, `api/models.py` — запросы и хранение в MongoDB
- `api/auth.py` — права эмулятора и сотрудников
- `api/errors.py`, `api/middleware.py` — ошибки и журналирование
- `api/management/commands/createoperator.py` — серверное создание сотрудников
- `config/` — конфигурация Django и OpenAPI

Миграции auth/contenttypes в `mongo_migrations/` адаптированы из Django 6.1.3
для ObjectId. При обновлении Django сверяйте их с upstream. Переноса старых
данных из SQLite нет. Истёкшие сессии удаляйте регулярно:

```bash
uv run python manage.py clearsessions
```

## Локации для выпадающего списка

`GET /api/v1/locations/` публично возвращает `{"items": [...]}`. Один элемент:

```json
{
  "id": "47.21997,39.70769",
  "name": "Ростов-на-Дону, Ростовская Область, Россия",
  "latitude": 47.21997,
  "longitude": 39.70769,
  "measurement_count": 24,
  "last_observed_at": "2026-11-04T14:00:00Z"
}
```

Это пример структуры ответа, не текущее содержимое базы. В список включаются
только координаты, для которых есть записи Measurement, в том числе исторические.
После удаления последнего измерения локация исчезнет из списка. Это наличие
данных, а не признак того, что эмулятор сейчас запущен.

Локации группируются по точной паре координат; название берётся из последнего
по observed_at измерения. При пустом названии показываются координаты.
Одинаковые координаты с разными station_id не создают дубликаты локаций.
Разные координаты в одном городе считаются разными локациями.
`location_id` в ответе измерения соответствует `id` элемента этого списка.
Для выбранной локации запрашивайте:

```text
/api/v1/measurements/?location_id=47.21997%2C39.70769&order=asc
/api/v1/measurements/latest/?location_id=47.21997%2C39.70769
```

Можно одновременно передавать период и остальные фильтры.
Входной контракт: исходные `metrics`, `observed_at`, `station_id`,
`latitude`, `longitude`, `location_name`, `source`. Выходной контракт
дополняется вычисленными и служебными полями сервера.
